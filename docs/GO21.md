# Baki Go 21 — Product surface

Customer-facing 21-day AI nutrition coaching experience.

Coach app remains existing Baki Go. Go21 reuses portal tokens, enrollments, V2 brain, Timeline, Attention.

## Routes

| Who | Path |
|-----|------|
| Coach activate | Customers → detail → **開通 21 天 AI 陪跑** → `/customers/[id]/start-21d` |
| Customer entry | `/c/{portalToken}/go21` (opaque token; not guessable IDs) |
| APIs | `/api/coaching/portal/[token]/go21/{context,baseline,start,chat}` |
| Reminder worker | `/api/coaching/go21/reminders/process` (cron secret) |

## Eligibility

Only experience-21d enrollments may access Go21 routes. Generic coaching portals receive 403.

## Lifecycle Day X

Authoritative Day 1 = `coaching_enrollments.started_at` (experience schedule).
`go21_started_at` gates chat onboarding only and does not shift Day X.
Checkpoint measurements count only on/after lifecycle anchor (ignore pre-cycle history).

## Structured data

Numeric fields require defensible evidence. Qualitative hydration (`今天水喝超少`) stores a note/signal — never invents `waterMl`.

## Photo + real-time vision

1. Customer attaches a photo in Go21 chat (optionally with text e.g. 「午餐」).
2. Client uploads to private `coaching-meal-photos` via existing meal photo API:
   - known primary slot → that slot
   - photo-only / unknown slot → `snacks` (storage only; **does not invent** breakfast/lunch/dinner)
3. Chat turn sets `photoUploaded: true` only after successful upload.
4. Server resolves the authoritative photo from the portal’s daily log (never trusts client storage paths).
5. Real-time vision (`observeCoachingMeals`) runs in the **same turn**; observation is cached on `coaching_meal_photos` (`067`).
6. Observation feeds AI Coach V2 as evidence (freeMessage + mealObservations) — not a calorie scanner.
7. Daily generation job reuses the cache when present to avoid duplicate vision spend.

Vision observation ≠ confirmed fact. Failed vision keeps the photo/meal and degrades chat gracefully.
